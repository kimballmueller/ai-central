The Jarvis Build Checklist

The video walks through the six layers. This is the part you actually work from — what to pick at each layer, the permission ladder that keeps the thing safe, the instruction files to copy, and the single workflow I'd build first. If you only take one thing from this page, take the permission ladder.

⏱ ~10 minute read 🔧 Do-it-yourself 📍 Written for operators, not engineers

🎯 The one-paragraph version: Jarvis is not one AI model and it is not a dashboard. It's six things working together — a computer that stays awake, a harness that lets a model take action, the model itself, connections to your tools, written instructions and memory, and skills on a schedule. Miss any one of them and you have a chatbot. Build them in order, give it one job, and make that job reliable before you add a second.

The six layers at a glance

Each layer answers a different question. The common failure is buying the last layer first — people start with the voice and the glowing interface, which is the only layer that does no work.

J — Job Runner Where does it live? A Mac mini left plugged in Running it on the laptop you close at 5pm

J — Job Runner: the machine that stays awake

The specific hardware barely matters. Uptime is the whole point. If your agent is supposed to check email every few minutes, it cannot live on a laptop that's asleep in a backpack. If it builds a report every morning, the machine has to be on when that report is scheduled.

A dedicated machine also gives the agent a physical home — one place that holds the files, runs the automations, and keeps working while your main computer is off.

OptionGood forWatch out for
Mac miniMost people — quiet, power-efficient, always onUpfront cost
Old laptop / desktopFree start, proving it outSleep settings will bite you
Linux boxComfortable in a terminalMore setup
Cloud serverNo hardware, access anywhereMonthly bill, your files live elsewhere
💡 On RAM: if you're calling cloud models through an API, the machine is mostly just coordinating and doesn't need to be powerful. RAM only becomes the deciding factor when you want to run local models on it.

Local or cloud? Both. Use a local model for cheap, repetitive, private work, and escalate the hard tasks to a stronger cloud model. Local models cost nothing per call and keep sensitive data on your machine; they're also less capable and want more RAM.

A — Agent Harness: intelligence vs. agency

The harness is the software sitting between the model and the rest of your computer. It's the difference between a model that answers and one that acts.

Without a harness, you can ask an AI to write an email. With one, it can read the email, check the relevant context, create a draft, and put it in front of you for approval inside Gmail.

The model provides intelligence. The harness provides agency. The harness is also what controls what the model can reach, which tools it may use, how long it can work, and what happens when it hits a problem.

It's what makes loops possible: read the task → make a plan → use a tool → check the result → keep going until done. That loop is the thing that makes an agent feel different from a chatbot.

⚠️ This is where people get burned. Do not give an agent unlimited access on day one. Start with one folder, one email label, and read-only wherever it's offered. Expand only as you learn how it behaves. An agent with full access and bad instructions doesn't get more useful — it gets more dangerous.

R — Reasoning Model: route work by cost

This is the LLM — OpenAI, Claude, Gemini, or something local. You don't have to pick just one, and a harness means your whole system isn't locked to a single AI company.

Think of it like assigning jobs to employees. You wouldn't pay your highest-level strategist to rename files all day.

TierWorkSend it to
Tier 1Cheap and repetitive — sorting, tagging, classifyingA small or local model
Tier 2Needs real writing or judgementA mid-tier cloud model
Tier 3Deep reasoning on a hard problemYour best model — only when needed

The goal isn't to use the best model for everything. It's to use the least expensive model that still reliably completes the task. API costs climb fast when every trivial job goes to the most expensive option.

V — Virtual Connections: where it gets hands

Two acronyms do the work here.

API (Application Programming Interface) is a structured way for one piece of software to talk to another. An email API lets your agent read messages or create drafts. A CRM API lets it update a contact. An analytics API lets it pull business numbers.

MCP (Model Context Protocol) gives models a standardised way to connect to tools and data. Instead of building a custom integration for every app, an MCP server exposes a specific set of tools the agent is allowed to use.

This is the layer where the agent gets hands — which is exactly why access should be deliberate. For every connection, decide separately whether it can read, write, delete, or send.

PermissionRiskRule of thumb
ReadLowerFine to start here on almost anything
Write / draftModerateGrant once you've watched it read for a while
DeleteHighWithhold. Let it propose, you execute
SendHighWithhold until it has earned it — see HITL below

HITL — Human In The Loop. The agent does most of the work, but a person stays at the decision point that matters. It prepares the proposal, you approve the pricing. It drafts the email, you approve the message. That's how you get the speed of AI without handing over the decisions you'd regret.

I — Instructions & Memory: the layer everyone skips

This is probably the most important part of the system. People assume the intelligence comes from the model, but the quality usually comes from the context you put around it.

Your agent needs to know who you are, what your company does, what you're working on right now, how you like things done, and what it must never do.

You don't need a database. Start with markdown files — plain text. One main file explaining the business, then an SOP per task.

Copy this as your starting business.md:

# Business Context

## What we do
[One paragraph. What you sell, to whom, and what makes you different.]

## Who we serve
[Ideal customer. Who is NOT a fit — this matters as much.]

## Current goals
[This quarter, in plain language. Update it when it changes.]

## Products & pricing
[What you sell and what it costs. Note anything that must never be
quoted without a human.]

## How we sound
[Tone. Words we use. Words we never use.]

## Hard rules — never do these
- Never send an email to a client without my approval
- Never quote a price not listed above
- Never delete anything
- Never respond to an angry customer; flag it to me instead

And an SOP looks like this — one per repeatable task:

# SOP: Morning Email Triage

## Input
Unread email in the inbox since the last run.

## Process
1. Sort into: needs a reply / FYI / ignore.
2. For "needs a reply", check the CRM for context on the sender.
3. Draft a reply in my voice and leave it in Drafts.

## Output
A list of drafted replies, plus a one-line summary of the FYI pile.

## Stopping condition
Stop and ask me if: the sender is angry, money is involved,
pricing is missing, or you are unsure who the sender is.

## Never
Send anything. Drafts only.
⚠️ Don't treat this like a prompt. Treat it like training an employee. If you'd explain something to a new hire, put it in the file. If you correct the agent twice, update the SOP. Every correction should improve the system — that's how this compounds. A chat disappears. A file gets better.

On memory: the agent shouldn't save everything. It should save preferences, decisions, product updates, and lessons that will matter in a future task. Memory isn't a transcript of what happened — it's the stuff you don't want to explain twice.

S — Skills, Schedules & Speech

A skill is a repeatable capability: check the inbox, build a report, create a proposal, research a prospect, repurpose content. Every skill needs four things — an input, a process, an output, and a stopping condition.

The stopping condition is the part people forget. The agent has to know when the task is finished, and just as importantly, when to stop and ask for help.

If…Then…
Pricing information is missingDon't create the proposal — ask
The customer is angryDon't send a response — flag it
It can't resolve the situationAsk for approval

A schedule is what lets work happen without you starting it. That's usually a cron job — cron being the scheduler that runs commands at set times. Check urgent email every few minutes; build a business report every morning; summarise open projects every Friday.

Triggers are the event-driven version: a new lead entering the CRM, a form submission, a failed payment. The trigger launches the skill, the skill follows the SOP, the agent uses the tools it's allowed, and the result either completes or comes to you for approval.

Speech is last for a reason. TTS (text-to-speech, via something like ElevenLabs) turns responses into voice; STT (speech-to-text) lets you talk instead of type. It's genuinely impressive — and it is the final layer, not the system. Don't start here.

The one workflow to build first

An email and daily business briefing agent. Every morning, automatically:

StepWhat it does
1Check the calendar and important unread email
2Check the CRM for leads that need attention
3Pull a small set of KPIs and compare to last period
4Write a short briefing: your messages, emails needing replies, leads to follow up, and the actions that matter most

Deliver it to Telegram, Slack, email, or a simple page. Later, connect ElevenLabs and have it read the briefing aloud.

That one workflow teaches you nearly everything — permissions, memory, SOPs, schedules, tool connections, and human approval. Don't start by asking your agent to run an entire company. Give it one job, make the job reliable, then add the next one.

Leverage, not autonomy

The goal was never full autonomy. It's useful leverage.

Give the agentKeep for yourself

I wouldn't let an early version of this independently send sensitive messages, move money, delete important files, or publish work without review. It can prepare those actions. It can recommend them. It shouldn't be the one to pull the trigger.
